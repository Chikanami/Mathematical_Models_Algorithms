## 1. 从原始式到软件架构

### 1.1 原始式

```
g( f₁(W₁), f₂(W₂), …, fₙ(Wₙ), h(M), P )
```

| 符号 | 原始语义 |
|---|---|
| `fₙ(Wₙ)` | 第 n 个实体、及其初始状态 |
| `h(M)` | 系统级交互规则：吃全部当前状态 → 返回后继状态 |
| `P` | 参数集（迭代规则、终止条件、规范化、变异算子） |
| `g` | 主驱动：组装三者并执行迭代 |

### 1.2 三个先例揭示的泛化路径

| | 实体数 | `h` 的性质 | `g` 的性质 |
|---|---|---|---|
| DICE | 2 | 单后继 + 实体自身变异 | 固定轮次迭代 |
| Mandelbrot | 2 | 单后继 + 逃逸判定 | 每点独立迭代 |
| WaterSort | n（JSON 动态生成） | **多后继（关系而非函数）** | BFS 遍历全状态空间 |

两处必须注意的先例：

- **`auto_generate_tube_fns()`**：`f` 可由外部数据动态生成。即模块不必手写，可从清单／契约生成——这正是"由 LLM 或开发人员产出模块"的现成接口位。
- **`generate_mandelbrot()`**：外层遍历网格，每个点调一次 `g`。这是 `g ∈ f` 的原始形态，当时尚未被形式化。

### 1.3 核心洞察：本架构 = 把集中式 `h` 分解到边上

理解全部后续内容的钥匙。

原式中，**所有交互都由唯一的全局函数 `h` 中介**。实体之间不直接相连，只与 `h` 相连。这是**星形拓扑**——中心 `h`，叶子是各实体。

本架构做的是：

```
h(M)  ⟹  分解为一组两两有向边 E ⊆ N × N，每条边自带接口属性
```

即：**原本集中在一个全局函数里的交互规则，被拆散、分布到图的边上，并成为一等公民。**

> 原仓库的 `h` 是本架构的**退化特例**——当所有交互都经过同一中介节点、且该节点承担全部规则时，图退化为星形，等价于 `h`。

这不是"另起一套"，而是**同一个式子的展开**：原式是本架构在"中介节点数为 1"时的坍缩形态。

### 1.4 提升映射表

| 原始 | 本架构 |
|---|---|
| `fₙ` | 模块的行为 |
| `Wₙ` | 模块的**绑定数据**（初始状态、配置、常量） |
| `h(M)` | **被分解**：不存在全局 `h`，交互即边 |
| `P` | 分散到：边属性、绑定数据、外部节点 |
| `g` | 组装器／运行时调度器；**其自身亦为模块**，可被更外层 `g` 使用 |
| `g ∈ f` | 模块集合在组合下**闭合**（子图可嵌套） |

### 1.5 一处语义差异的澄清

原式 `fₙ(Wₙ)` 有两种读法，不等价：

- **读法 A**：`fₙ` 是函数，`Wₙ` 是它作用的参数（Mandelbrot：`f₁ = z ↦ z²`，`W₁ = z`）
- **读法 B**：`fₙ` 是空参函数，返回初始状态（DICE：`f1()` 直接返回列表）

本规范采用**读法 A**，并区分：

```
模块 n := ( μₙ , Wₙ )
           ↑     ↑
          行为   绑定数据
```

原式没有"运行期输入"概念——一切输入都经 `h` 中转。本架构的模块**可以**有来自边的运行期输入，这是 §2–§4 要补的。

## 2. 两个正交轴：功能与接口

### 2.1 正交，不是从属

**模块与接口不是从属关系。**

```
功能轴 F ：模块实现什么
接口轴 I ：输入与输出是什么格式
```

二者独立取值。示例：

```
f1(x,y) = x * y          f2(x,y) = x ^ y
```

`*` 与 `^` 是 `F` 上的两点；标量／矩阵／高阶张量／事件触发器是 `I` 上的点。任意组合都有意义：

- 相同格式的输入输出，可以放在不同功能上（`*` 和 `^` 都可以是标量接口，也可以是矩阵接口）
- 相同接口可以用在各种模块上（标量接口可用于任意二元运算模块）

### 2.2 需求键 = `F × I` 上的一个点

回头看需求键五元组，它其实是 **1 + 4 的分解**，不是五个并列项：

```
[ 功能 , 输入数据 , 输入格式与结构 , 输出数据 , 输出格式与结构 ]
   └1┘   └─────────────────4──────────────────┘
  功能轴 F                接口轴 I
```

**需求键 := `(f_req, i_req) ∈ F × I`。**

这个分解解释了需求键为何是五项：它同时命名了两个正交轴上的坐标。也是为什么它足以确定一个模块的生成目标，又足以确定一次连接的合法性。

### 2.3 复用性：由结构等价诱导的二部关系

"相同接口用在各种模块上"与"相同格式放在不同功能上"，是同一个关联关系的两个方向：

```
Supp ⊆ M × (I / ≅)
```

- `M` ：模块集合
- `I / ≅` ：**描述符按结构等价取商集**（不是有身份的接口实体，见 §4.2）
- `(m, [i]) ∈ Supp` ⟺ 模块 `m` 支持结构等价类 `[i]`

方向读法：

- 一个 `[i]` 关联多个 `m` ⟺ 相同接口用在各种模块上
- 一个 `m` 关联多个 `[i]` ⟺ 相同格式放在不同功能上

**这个二部关系是复用性的全部形式内容。** 它与 §4 的"模块关系图"是**两个不同的结构**：前者管复用，后者管拓扑。

**注意**：`I / ≅` 是**计算出来的**，不是声明的。没有接口实体，等价类由描述符的结构比较导出。这使 `Supp` 成为一个**导出结构**而非一等公民——省去了一层维护，代价是每次判定需做结构比较（可缓存）。

### 2.4 一个必须承认的后果

`*` 这个功能，在标量接口下与矩阵接口下，**实现是两段不同的代码**。

> 功能与接口正交，但**功能的实现依赖接口**。

所以模块不是"一个恰好能收多种格式的函数"，而是——见 §3。

## 3. 模块：纤维化定义

### 3.1 定义

```
μ            := 一个模块
dom(μ) ⊆ I   := 该模块支持的格式集合（它的"接口论域"）
μ(i)         := 在格式 i 下的具体行为，i ∈ dom(μ)
```

即模块是**以接口为索引的行为族**：

```
μ : I ⊇ dom(μ) → ( X_i → Y_i )
```

### 3.2 `dom(μ)` 与边上的接口是两回事

这是本版最容易混淆、也最关键的一处区分：

| | 归属 | 含义 |
|---|---|---|
| `dom(μ)` | **模块** | 该模块**能**接受哪些格式 |
| 边的接口描述符 | **边** | 这次连接**实际用**哪个格式 |

模块声明**能力**，边固定**选择**。两者都不越界。

这条区分修正了 v1 的一处错误论断（v1 称"无边模块无契约"）：**无边模块并非无契约，而是有论域、未绑定**。它的 `dom(μ)` 仍然完整存在，可被独立审查。

### 3.3 三种情形统一在一个定义下

| 情形 | 形式 |
|---|---|
| 单接口模块 | `\|dom(μ)\| = 1` |
| 多接口模块（重载／dispatch） | `\|dom(μ)\| > 1`，由接口选实现 |
| **接口作为输入输出控制** | 接口标签本身是**显式输入**，参与行为决定 |

**第三行就是你提的"通过定义接口来做输入输出控制"。** 接口在此不只是描述，**是控制信号**。描述性与控制性这两个角色，形式上是同一个 `i`：描述性来自 `i` 作为类型标签，控制性来自 `i` 作为 `μ` 的索引。

### 3.4 附带收益

§7 的"受控可变性"因此获得一条**比 v1 方案更轻**的变更手段：

> 若模块已支持多接口（`|dom(μ)| > 1`），**只改边上的接口描述符就能改行为，模块体完全不动**。

不需要版本化、不需要适配器、不需要留痕（因为模块体确实没变）。这是"接口作为控制"带来的直接工程红利。

## 4. 边：接口即边属性

### 4.1 定义

```
边 e := ( src , dst , Dₑ , Φₑ )
         ↑     ↑     ↑    ↑
       源模块 目标模块 接口描述符 效应标注
```

### 4.2 统一结构化接口

本架构**采用统一结构化（structural）接口建模**：

> 接口**就是**格式描述符本身，内联在边上。**不引入接口实体，不引入接口层。**

- 两条边的接口"相同" ⟺ 描述符**结构相等**（`≅`）
- 无身份、无引用、无共享
- 改一处描述符**不影响**任何其他边

**收益**：

1. **概念最少。** 全图只有一种节点（模块）、一种边（连接）。图同质，无需第二层。
2. **不变量最少。** 无需维护"接口实体 ↔ 边引用"的一致性。
3. **适配器这个特殊机制整个消失。** 见 §4.4。
4. **与"接口是边的属性"完全自洽**，无需修正你的原始表述。

**代价（登记，不掩饰）**：

1. **无法表达接口的版本、特化、显式兼容声明。** 这些只能通过描述符**自身的结构**表达（如描述符内含版本字段），不能作为一等概念。
2. **事件触发器类接口需要额外处理**，见 §8.3。
3. **`I / ≅` 需要计算**（§2.3），且结构比较可能昂贵（描述符嵌套深时）。可缓存，但不能免除。

### 4.3 描述符必须机器可校验

描述符是**可计算**的结构，不是文档里的自然语言约定。起步用 JSON Schema 一类即可，要求覆盖：类型、必填性、取值范围、结构嵌套。

**仅靠自然语言约定"输入输出接口"不足以支撑自动组装**——组装器必须能判定 `≅`，这必须是可计算的。

### 4.4 适配器就是普通模块

统一结构化带来一个漂亮的消解：

v1 曾计划给边加一个 `适配声明` 字段来承载适配。在结构化模型下**不需要**：

> **适配器 := 一个普通模块 `A`，满足 `dom(A) ∋ D_上游输出` 且 `A(D_上游输出)` 的输出描述符 `≅ D_下游输入`。**

它是图上一个正常节点，走正常的边，受 §7 的类型检查约束。**没有新概念，没有新机制。**

### 4.5 效应标注

因一切读／写／硬件／env 操作都被视为输出维度，边必须声明其**效应**：

```
Φₑ ∈ { 纯 , 读 , 写 , 读改 , 非确定 }
```

`Φₑ` 是**边局部属性**，不属于描述符 `Dₑ`——因为同一条描述符在不同连接下效应可以不同（如"写本地缓存"与"写远端库"）。

这不是装饰。它决定组装器的三项能力：

- **能否重排**：纯边之间可任意换序；写边之间不可
- **能否并行**：纯边可并行；含写边需检查是否触及同一外部节点
- **能否重放**：非确定边不可重放，追踪时须记录实际取值

**缺了效应标注，组装器只能保守串行化一切，架构的性能优势归零。**

## 5. 纯函数 vs 关系（多后继）

`h` 在 WaterSort 中返回后继**列表**而非单一后继。这一性质必须在架构层面显式化——它决定运行期引擎的形态。

### 5.1 定义

```
模块语义 := 关系 R ⊆ X × Y
函数     := 满足 ∀x, |R(x)| = 1 的特例
```

### 5.2 组装语义分叉

| 模块类型 | 组装语义 | 运行期引擎 |
|---|---|---|
| 函数型（单后继） | 串行管道 | 直接调用 |
| 关系型（多后继） | 状态空间展开 | 搜索（BFS／DFS／启发式） |

**这是架构的第二个分叉点**（第一个是 §1.3 的集中 vs 分布）。

关系型模块的存在意味着：一条组装路径可能对应**一棵执行树**而非一条流水线。组装器必须知道每个模块属于哪类，否则无法选引擎。

原仓库已把两种引擎都演示了：DICE／Mandelbrot 是函数型，WaterSort 是关系型。

## 6. 副作用与高出入度节点

### 6.1 隐式输入是追踪盲区

你列举的输入维度中，**读操作类的是隐式输入**：读文件、硬件输入、环境变量、外部变量、全局环境。

纯函数视角下，"读了一次环境变量"不体现在签名里。不写进契约就无法被数据流追踪覆盖，追踪会在此**静默断裂**——而且因为是隐式的，你甚至不会知道断裂发生了。

**硬约束**：一切隐式输入必须**显式化为边**，连到代表该外部系统的节点。禁止模块直接触碰未建模的外部状态。

放宽这条，架构最核心的卖点（通过数据流追踪根因）即失效。

### 6.2 高出入度节点（hub）问题

数据库、环境变量、全局状态、状态机变量在图中表现为**极高出入度的 hub**。

hub 会**破坏可达性判断**：任意两个模块几乎都能"经由全局状态连通"，于是"从输入描述符可达输出描述符"这一判据退化为恒真，检索与组装同时失效。

必须施加**受限穿透**规则，例如：

- 默认禁止路径穿过 hub
- hub 只在其边被**显式声明**时才允许参与
- 按效应标注加权，穿透 hub 的路径付出更高代价

**这是图模型能否可用的关键，是文档 2 的核心议题。** 此处仅登记其必然性。

### 6.3 追踪的边界

承认两处追踪必然终止：

1. **外部节点内部**——不可形式化，只能作为黑箱约束在边上
2. **非确定边的实际取值**——只能记录当次实际结果

诚实标注边界，比假装全能更有价值。

## 7. 受控接口可变性

### 7.1 立场

你提出"模块不是不可变的，可以按需调整输入输出接口"。经 §2、§3 的分解，这条被**精确化为三个不同层次**：

| 变更对象 | 机制 | 代价 |
|---|---|---|
| **改这次连接用哪个格式** | 改边上的描述符 `Dₑ`（若 `\|dom(μ)\| > 1`） | **最低**，模块体不动 |
| **改连接的契约本身** | 新增／替换一条边 | 中，需留痕 |
| **改模块支持的能力** | 改 `dom(μ)`，即改模块 | 最高，动模块体 |

**关键结论：变的通常不是模块，是边。** 三个层次代价递增，应优先用低层手段。

### 7.2 留痕规则

即便变的只是边，仍需约束，否则可追踪性会流失：

1. **版本化、只追加。** 版本化的对象是**边**（及其描述符），不是接口——结构化模型下接口无实体，谈不上版本（见 §4.2 代价 1）。旧边不删除，降级为历史。
2. **留痕必须含方向。** 记录"谁改的、因哪个消费者的需求、旧描述符是什么"。**变更权力向上游传播**——是消费者需求驱动生产者调整；方向不记录则溯源断裂。
3. **优先走最低层次。** 能用改描述符解决的，不要改模块。

### 7.3 结构化的补偿

结构化模型没有"接口版本"，但**描述符内部可以有版本字段**，以纯数据方式获得等效能力。这是把一等概念降级为数据字段的典型代价：能表达，但不能被组装器原生理解。

## 8. `g ∈ f`：闭合性与分形嵌套

### 8.1 一阶闭合

> 模块集合在组合下**闭合**——组装结果 `g` 本身可作模块 `f`，参与更外层组装。

图上对应**子图嵌套**：

```
子图 S ⊆ 全图
S 的外部边集（一端在内、一端在外） := S 的接口
```

`S` 可被折叠为单个节点，其接口即上述外部边集。折叠后的节点与普通模块在设计上不可区分——**这正是分形性的内容**。

### 8.2 闭合的成立条件

`S` 可折叠为单个模块，当且仅当：

1. `S` 的外部边集完整声明了 `S` 与外界的全部交互（**无隐式通道**）
2. `S` 内部的所有 hub 访问都已被外部边覆盖

**条件 1 是全部难点。** 只要 `S` 内有一条绕过外部边集的隐式交互（偷读全局变量、偷偷写日志），折叠就是错的——得到的模块换个环境行为就不同。

这也是 §6.1 那条硬约束的第二个理由：**隐式输入不仅破坏追踪，还破坏闭合性。**

### 8.3 二阶闭合：接口词汇表本身由模块组合生成

你指出"事件触发器本身也可以用一堆模块拼出来"。这句的后果比看上去大：

```
接口 i_event  :=  一个子图 S_event
```

即**接口的载体本身是本架构的产物**。这比 `g ∈ f` 更强：

| | 内容 |
|---|---|
| 一阶闭合 `g ∈ f` | 模块组合的结果，可再作模块 |
| **二阶闭合（新）** | **接口词汇表本身，由模块组合生成** |

`I` 与"模块组合"不是分层关系，而是**互相嵌套**。

#### 结构化模型下的问题与缓解

统一结构化（§4.2）下，接口只是描述符。若事件触发器的语义由子图决定，则**两份结构相同的描述符可能行为不同**——架构无法区分。这是选择结构化所接受的限制。

**缓解方案**：描述符中嵌入子图的**规范化摘要**（canonical digest）：

```
D_event := ( 结构描述 , digest(S_event) )
```

于是描述符的结构相等 **蕴含** 语义相等（至摘要碰撞）。

**必须如实说明**：这在实质上把名义化伪装成了结构化——用内容寻址（content addressing）替代实体身份。代价有二：

1. **摘要计算需要全图规范化**，图规模大时昂贵
2. **摘要碰撞不可完全排除**（概率极低但非零）

这是本架构在"概念最少"与"语义可区分"之间所做的取舍，登记为已知代价。

### 8.4 类型检查在 wiring 粒度

由 §3.2，模块与其连接分离，因此：

```
✓ 模块粒度：对每个 i ∈ dom(μ)，检查 μ(i) 是否正确实现  （功能正确性）
✓ wiring 粒度：检查相邻边 e₁: A→B 与 e₂: B→C 是否兼容  （连接正确性）
```

`B` 处需校验：`B` 能否把 `e₁` 的输出描述符实现为 `e₂` 的输入描述符，即

```
D_{e₁}.out  ∈ dom(μ_B)   且   μ_B(D_{e₁}.out).out  ≅  D_{e₂}.in
```

**这是本架构在工程上最实质的变化**：类型系统的单位从"模块"上移到"连接"；而模块自身只需为其论域内的每一项负责。

相比 v1 的判断，这是一处**修正**：模块并非"无法被孤立审查"，而是**功能正确性与连接正确性分离到两个粒度上审**。

### 8.5 深度上限与粒度准则（未定）

闭合性允许无限套娃，工程上不可行。需要：

- **深度上限**：嵌套层数到多少为止
- **粒度准则**：多小算一个模块

两者**目前无依据可依，需经验确定**。登记为待决项，并提示：**若团队不统一粒度准则，各人会各自为政，最终模块边界互相冲突，复用率反降。** 不解决这条，架构的规模优势无法兑现。

## 9. 物理实体与逻辑实体

### 9.1 两个层次

```
逻辑实体 ：图上的一个节点（一个模块）
物理实体 ：一个或一组代码文件（.py / .cs / .jar / .fsx / …）
```

这是**多对多**：

- 一个模块可跨多文件 → 组装时需处理依赖与打包
- 一个文件也可承载多个模块（如一个 `.py` 内多个函数） → 打包时易漏

**必须显式记录这个映射**，否则打包会漏模块。

### 9.2 组装与打包是两个独立操作

> **组装（逻辑连线）** 与 **打包（物理落盘／进程边界）** 是两个独立操作。

同一份逻辑图，可以用不同物理映射实现，得到不同部署形态（单体／多进程／跨语言服务）。

### 9.3 物理映射决定边的"收费"与否

逻辑上相邻的两个模块，物理上可能同进程，也可能跨进程跨语言。于是：

| 物理边界 | 后果 | 对闭合性（§8.2）的影响 |
|---|---|---|
| 同进程（同一 `.py`） | 可共享内存，隐式状态容易藏匿 | **更难**满足 |
| 跨进程／跨语言 | 强制序列化，隐式状态被迫显式化 | **更易**满足 |

**物理映射决定了哪些逻辑边是"免费"的、哪些是"收费"的。**

这把"多语言模块"从一条孤立观察（§10.1）变成了**可计算的设计变量**：需要闭合性时，有意识地在该子图边界上引入物理边界。

## 10. 语言中立契约

### 10.1 多语言是本架构的天然支持项

契约从一开始就不在语言里，而在边上（§4.2 结构化描述符），所以多语言在形式上不构成问题。

跨语言边界天然是**序列化边界**，带来一个反直觉的好处：

> 跨语言强制显式序列化 ⟹ 隐式状态被迫显式化 ⟹ **§8.2 的闭合条件更容易满足**

即：**多语言模块混用，反而强化了架构最重要的那条性质。** 同语言模块之间容易偷偷共享内存状态，跨语言则不可能。

### 10.2 描述符的表示

语言中立形式，起步 JSON Schema 即可，无需更重的方案（§4.3）。

### 10.3 错误是输出维度

跨语言时各语言的异常／错误模型不一致。描述符需把**错误作为一种输出**显式声明，否则错误路径成为图示之外的隐式通道，再次破坏 §8.2 的闭合条件。

## 12. 与既有主张的差异汇总

### 12.1 本轮（v1 → v2）的修订

| v1 说法 | v2 修订 | 依据 |
|---|---|---|
| 需求键归属待决，倾向属于边 | **伪二分**，需求键 = `F × I` 上的点 | 你指出模块与接口非从属 |
| 模块是单一行为映射 | 模块**纤维化** `μ : I → (X_i → Y_i)` | 同一功能在不同格式下实现不同 |
| — | 新增 `dom(μ)`（模块能力）与边上描述符（本次选择）的区分 | 你的澄清 |
| 无边模块无契约 | **无边模块有论域、未绑定** | §3.2 |
| 接口变更需版本化＋适配器 | 三层变更，**最轻一层只需改描述符** | §3.4 接口作为控制 |
| 适配器需专门的 `适配声明` 字段 | **适配器就是普通模块**，机制消失 | 统一结构化 |
| 模块无法被孤立审查 | 功能正确性与连接正确性**分离到两个粒度** | §8.4 |
| 接口可变性需靠留痕保护 | 结构化模型下**接口无实体可版本化**，版本化对象是边 | §4.2 代价 1 |

### 12.2 与最初设想的差异（延续 v1 并保留）

| 初始设想 | 本规范 | 理由 |
|---|---|---|
| 模块可调整输入输出接口 | 变的通常是**边**，模块体不变 | 否则追踪与审查基准漂移 |
| 小模块审查难度低 | 审查分两个粒度：模块（功能）／wiring（连接） | §8.4 |
| 数据流可追踪根因 | 追踪在外部节点内部、非确定边处终止 | §6.3 |
| 高出入度节点只是"度特别高" | hub 会破坏可达性判断，需受限穿透 | §6.2 |
| 接口的可复用性 | 由**结构等价类**承载，是导出结构而非一等公民 | §2.3、§4.2 |
